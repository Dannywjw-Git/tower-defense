# 真机验收清单（Phase 7）

> spec §7.2 的五条**必须在真实设备上取证**。
> 桌面无头浏览器**不能替代** —— iOS 微信与安卓 X5 内核的行为无法在桌面复现。

---

## 需要的设备

- 一台**安卓手机**（中端为佳，这是 spec 定下的验收基准）
- 一台 **iOS 手机**（用于验证"微信内可玩"）
- 手机与电脑连**同一 WiFi**

---

## 准备：启动本地预览

```powershell
cd D:\Users\Danny\Documents\tower-defense
node scripts\serve.js 8788
```

手机会访问 `http://192.168.1.8:8788/`（脚本启动时会打印可用地址）。

## ① 帧率 ≥ 30 fps

**环境**：中端安卓 + **微信内置浏览器** + 满波（≈30 怪 + 15 塔）

**步骤**：
1. 微信里打开 `http://192.168.1.8:8788/`
2. 进入地图 2「转弯」（12 波，敌人最多）
3. 用「2×」加速到后期波次，或反复建塔把场面撑满
4. 观察画面是否卡顿；游戏底部提示条会显示 `cell XXpx` 等实时信息

**判定**：画面流畅、无卡顿跳帧 → 通过

---

## ② 竖屏格子 ≥ 44 px

**步骤**：
1. 手机**竖着**拿（不要横屏）
2. 进入任意地图
3. 点建造栏的塔图标 → 观察绿色可建格
4. 用指尖逐个点击几个格子的**中心与边缘**

**判定**：每次点击都能准确落在目标格，无"点 A 建到 B" → 通过

游戏底部会显示 `cell XXpx`，可直接读数值。**应 ≥44**。

---

## ③ 首屏 ≤ 5 秒

**步骤**：
1. 手机浏览器**开无痕/清缓存**（避免缓存干扰）
2. 记录从点击链接到**看到「开始游戏」按钮**的时间

**判定**：≤5 秒 → 通过

> 参考：引擎 1061 KB，gzip 后约 300 KB。素材目前是代码绘制，体积很小。

---

## ④ iOS 微信可玩

**步骤**：
1. iOS 微信里打开链接
2. 确认能进入游戏（**不需要横屏**，这是 Phase 0 专门改的架构）
3. 玩一小段：建塔、点敌人补刀、暂停

**判定**：能正常游玩，无需旋转手机 → 通过

> 这是 Phase 0 抓出的关键问题：原设计的「请横屏游玩」遮罩在 iOS 微信里
> 等于永久提示牌（`screen.orientation.lock()` 需全屏且可能被拦截）。
> 现改为 8 列大格子 + 三朝向自适应。

---

## ⑤ 切后台自动暂停

**步骤**：
1. 游戏中**记住当前波次与场上敌人数**
2. 切出去（回微信消息 / 按 Home）
3. **等 30 秒**
4. 切回游戏

**判定**：HUD 显示「⏸ 已暂停」，且波次计时与敌人位置**没有推进** → 通过

## 未通过时怎么办

| 失败项 | 处置 |
|---|---|
| 帧率不足 | 先减特效 → 再降实体上限 → 最后才考虑减塔种（spec §9 回退表） |
| 格子过小 | 地图放宽到 9×5（45 格，竖屏每格约 41 px），见 spec §6.1 预留方案 |
| 首屏过长 | 检查网络；必要时把 `vendor/phaser.min.js` 换 CDN（代价是依赖第三方可用性） |
| iOS 微信打不开 | 用 probe 页定位是渲染问题还是加载问题 |
| 切后台未暂停 | 检查 `GameScene.setupVisibilityPause` 是否被正确调用（微信 X5 的 `visibilitychange` 行为可能不同） |

## 顺带记录的两条手感项（非硬性）

- **建塔手感**：点图标 → 点格子的两段式操作是否顺手
- **出售二次确认**：是否觉得多余 / 是否真能防误触

这两条是 spec §6 的设计假设，真机体验会告诉我们是否要改。
