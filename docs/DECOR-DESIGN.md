## 1. 目标与已定的取舍

**目标**：给地图加「有质感」的细节，同时**不牺牲可读性**、**不显著增加体积**。

**为什么是方向 2B**（我替你做的工程判断，理由如下）：

| 候选项 | 问题 |
|---|---|
| 方向 1 纯代码地形 | 放弃了质感（用户明确要 B「有质感」） |
| 方向 2A 草地底 + 装饰 | 要**改掉现有整套蓝灰配色**，风险大、改动面广 |
| **方向 2B 保留现有地面 + 装饰** | **零取舍**：不动配色、加真质感、仅 +10.7 KB ⭐ |
| 方向 3 autotiling | 工作量翻倍，且与「看清哪格能建」冲突 |

> **2B 是唯一没有取舍的方案**，所以我按它推进。
> 但实现里会把「地面配色」留成**一个可切换的开关**，你回来若想换成 2A，
> 改一个常量即可（见 §6）。

**探测已证明的关键事实**（不再重复论证）：
- Kenney 的草/泥地砖是**纯色块**（`颜色数=1`），贴上去与代码绘制**肉眼不可区分** → **不贴地砖**
- 但 **frame 130–137**（灌木/树叶/苔藓/星形植物/石头）**带透明底、真有细节** → **只用这 8 张**

## 2. 素材方案（回答 grill-me 支柱 1：体积）

**只导出用到的 8 张散图**，不提交 3.86 MB 整包、也不提交 229 KB 图集。

| 项 | 值 |
|---|---|
| 8 张 64×64 PNG（实测） | **10.7 KB** |
| 放置位置 | `assets/decor/decor_130.png` … `decor_137.png` |
| 传输增量（gzip 后，PNG 已压缩） | **约 +10.7 KB** |
| 传输量：319 KB → | **约 330 KB** |
| 首屏（4G 实测 3742ms）→ | **约 3780ms**（仍 ≤5000ms，余量 ~1.2s） |

**DPR 处理**：素材是 64×64。手机 DPR=2 时格子约 46 CSS px（92 逻辑 px），
把 64px 图放大到 92 逻辑 px 是 **1.44 倍放大** —— 会有轻微软化。
**对策**：`setDisplaySize` 时开启线性过滤（Phaser 默认），
且装饰物本身是柔和形状（灌木/石头），**放大不露像素感**。
> 这与「塔的矢量图标」不同：图标是矢量，装饰是位图。可接受，因为装饰不需要锐利边缘。

**另存一份 @2 版本？** 不存。64→92 是 1.44 倍，未到 2 倍，存 @2 是浪费体积换几乎看不见的收益。

## 3. 架构与数据流

### 关键约束（读代码后确认的）

| 事实 | 位置 | 影响 |
|---|---|---|
| `draw()` 会被**反复调用**（每次 `setBuildMode`、每次重布局） | `GameScene.js:139,506` | ⚠️ **装饰物绝不能在 `draw()` 里创建**，否则会重复创建 → 对象泄漏 |
| 场景有 `shutdown` 钩子（现有监听器清理就在这里） | `GameScene.js:524` | 装饰物必须挂同样的清理 |
| 地面用**一个** `Graphics`（`this.g`，depth 0） | `GameScene.js:92` | 地面不改，装饰叠在其上 |
| 塔 depth = 2 | `Tower.js:126` | 装饰必须 **depth < 2** |
| 素材清单设计意图：**「只改 assets.js + BootScene，逻辑代码零改动」** | `assets/assets.js` 头注释 | 遵循它 |

### 分层

```
depth 0.0  this.g          地面（现有，不改）
depth 0.8  decor 精灵       ← 新增（本次）
depth 2    Tower           塔（现有）
depth ...  敌人 / 弹道 / 特效（现有）
```

### 新增/改动文件（**4 个**，含 1 个新文件）

| 文件 | 改动 | 说明 |
|---|---|---|
| `assets/decor/*.png` | **新增 8 张** | 从图集导出，共 10.7 KB |
| `assets/assets.js` | 填 `IMAGES` 数组 | **唯一素材来源**（spec §6.6），符合其设计意图 |
| `src/scenes/BootScene.js` | 加加载循环 | 按 `IMAGES` 预加载 |
| `src/systems/Decor.js` | **新增** | 装饰布局：**纯函数**，可 node 测 |
| `src/scenes/GameScene.js` | `draw()` 里只画地面；**新建 `buildDecor()`** 在 `create()` 与重布局时调用 | 避免在 draw 里重复创建 |

> ⚠️ 比初始估计多了 1 个文件（`Decor.js`）—— 因为**布局逻辑要可测**。
> 放在 `GameScene` 里就没法用纯 node 断言（项目的 `logic-check` 都是纯逻辑模块）。

## 4. 装饰布局规则（`Decor.js`，纯函数）

```js
import { layoutDecor } from '../systems/Decor.js'
// 返回 [{ cx, cy, key, scale, kind }]，确定性（同一关永远同一布局）
```

**规则**（每条都对应一个已识别的风险）：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **只放在 `buildable` 格** | 放在路径上会挡住敌人与路；放在 blocked 上语义混乱 |
| 2 | **只装饰约 38%** 的可建格 | 全放会花；38% 是原型实测的舒服值 |
| 3 | **确定性伪随机**（`hash(cx,cy)`，不用 `Math.random`） | 否则每次重布局装饰都会"跳"，玩家会看到闪烁 |
| 4 | **尺寸 42–56% 格宽**（石头小、灌木大） | 太大挡塔、太小看不见 |
| 5 | **贴格底**（y 偏下 0.60 格） | 有"长在地上"的感觉，而不是浮在格中央 |
| 6 | **alpha 0.9** | 避免喧宾夺主 |
| 7 | **depth 0.8 < 塔的 2** | 保证塔永远压在上面 |
| 8 | **不在有塔的格子放** | 建塔后装饰若还在，会与塔重叠（见 §5 处理） |

**建塔后怎么办？** 装饰按**格子坐标**索引。`buildTower` 成功时，
把该格装饰 `setVisible(false)`；卖塔时恢复。**这样一个 Map 查询搞定，不用重建。**

## 5. 风险与缓解（回答 grill-me 支柱 2、3）

| # | 风险 | 缓解 | 状态 |
|---|---|---|---|
| **R1** | 装饰物挡住塔/敌人，影响可玩性 | depth 0.8 + 只占 42-56% + 贴格底 + 建塔即隐藏 | 原型已实测 |
| **R2** | `draw()` 被反复调用导致装饰重复创建 | 装饰**不在 `draw()` 里创建**，独立 `buildDecor()` + shutdown 清理 | 已识别 |
| **R3** | 场景重启/换关时对象泄漏 | 挂 `shutdown` 钩子销毁；`stress-flow` 有泄漏断言 | 待实现验证 |
| **R4** | 首次加载多 8 个请求 | 8 个小 PNG，HTTP/2 多路复用；且 <11 KB | 低 |
| **R5** | 手机掉帧（验收线 ≥30fps） | 40 格里约 15 个装饰 → 15 个静态精灵，**不进 update 循环**，无每帧开销 | 低，但**真机需确认** |
| **R6** | 现有 42 项 `visual-flow` 断言被破坏 | 装饰是**新增**层，不改地面/塔/敌人几何 → 预计零破坏。若不通过会**如实修正断言并说明** | 待验证 |
| **R7** | 装饰遮住「可建格」绿色高亮 | 建造模式下装饰 alpha 降到 0.35 | 待实现 |

**≥3 个风险缓解计划**已给出（R1/R2/R3 为实质风险，其余为低风险）——
满足 grill-me 的通过标准。

## 6. 可切换的开关（留校准旋钮）

ponytail 要求「硬件不是纸面理想，留下调校旋钮」。本设计留 **3 个常量**在 `Decor.js` 顶部：

```js
export const DECOR_DENSITY = 0.38   // 装饰密度（0=关掉，风格分歧时的开关）
export const DECOR_ALPHA   = 0.90   // 装饰透明度
export const TINT_MODE     = 'none' // 'none' | 'muted' —— 若想试方向 2A 的压暗观感
```

另有总开关：**`DECOR_DENSITY = 0` 即完全关闭装饰**（等价于方向 1/现状），
便于「不喜欢就一秒回退」。

### 实现中发现并修掉的问题（都是看图/断言抓出来的）

| # | 问题 | 怎么发现的 | 修法 |
|---|---|---|---|
| 1 | **`buildDecor()` 返回 0 个装饰** | 冒烟测试 `decor: 0` | 我把 `buildDecor()` 放在 `layout()` 之前，而 `L` 是 `layout()` 里才算的 → 守卫 `if (!this.L)` 直接 return。**改成先 `layout()` 再 `buildDecor()`** |
| 2 | **hash 只输出 0–0.5** | `decor-check` 的密度断言报 `0.769` 而非 `0.38` | 初版哈希在高位不进符号位，大样本 10 桶只有前 5 个有值（偏差 104.8%）。换成 xorshift 混合 → 偏差 2.8% |
| 3 | **装饰与箭塔撞色** | **看截图** —— 灌木和箭塔看起来是一类东西 | 实测：箭塔 `#4ADE80` vs 灌木 `#2ECC71`，**色距仅 37**（人眼 <40 分不开）→ 加 `setTint(0x7d9c7d)` 压暗降饱和 |
| 4 | 密度太低（仅 7 个） | 看截图觉得稀 | 每关只 24–26 可建格，0.38 → 7 个。提到 **0.62** → 15 个 |

> **教训（再次印证 HANDOFF §4.3 那条铁律）**：问题 1、3、4 **测试全绿**，
> 只有**冒烟查询 + 看图**才暴露。问题 2 则是断言抓的 —— 两者互补，缺一不可。
